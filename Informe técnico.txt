INFORME TÉCNICO DE INGENIERÍA DE SOFTWARE
Sistema Integral de Gestión Comercial, Ventas, Caja e Inventario
D' Kiram Pastelería
1. Resumen ejecutivo
D' Kiram Pastelería requiere un sistema que permita administrar de manera centralizada sus productos, categorías, inventario, ventas, métodos de pago, caja y turnos de empleados.
El sistema será diseñado como una aplicación web Mobile First y PWA, permitiendo su utilización principalmente desde teléfonos y tablets, sin excluir computadoras.
La arquitectura será un monolito modular, utilizando React + TypeScript para el frontend y Java + Spring Boot para el backend, con PostgreSQL como sistema gestor de base de datos y Supabase como proveedor de PostgreSQL administrado.
La solución separará explícitamente venta, detalle de venta, pago, caja, movimiento de caja, inventario, movimiento de inventario y turno de empleado para mantener consistencia transaccional y trazabilidad.
2. Objetivo general
Desarrollar un sistema web/PWA para D' Kiram Pastelería que permita gestionar integralmente productos, categorías, inventario, ventas, pagos, caja y turnos de empleados, proporcionando información operacional y reportes para facilitar el control diario del negocio.
3. Objetivos específicos
Administrar productos y categorías.
Controlar cantidades disponibles de inventario.
Registrar entradas, salidas, mermas y ajustes.
Registrar ventas con uno o varios productos.
Registrar pagos en efectivo, Yape y Plin.
Permitir excepcionalmente pagos divididos entre dos métodos.
Gestionar apertura y cierre de caja.
Determinar efectivo esperado y efectivo contado.
Detectar diferencias de caja.
Gestionar empleados y turnos.
Aplicar control de acceso por roles.
Generar reportes de ventas, caja e inventario.
Mantener trazabilidad de operaciones críticas.
Permitir crecimiento futuro hacia pedidos, clientes, delivery y comprobantes electrónicos.
4. Alcance del sistema
4.1 Alcance del MVP
Autenticación: inicio/cierre de sesión, recuperación de acceso, control de sesiones, roles y permisos.
Productos: CRUD, precios, costos, stock, stock mínimo, unidad, descripción, imagen y estado.
Categorías: Tortas; Postres; Pasteles y Queques; Bocaditos; Bebidas; Regalos / Extras.
Ventas: nueva venta, búsqueda, carrito, cantidades, cálculo automático, descuento autorizado, confirmación, anulación controlada e historial.
Pagos: Efectivo, Yape, Plin y pago mixto.
Caja: apertura, estado, movimientos, cierre, arqueo y diferencias.
Inventario: entradas, salidas, mermas, ajustes, historial y alertas.
Empleados: CRUD, roles, turnos y estado.
Reportes: ventas, caja, métodos de pago, inventario, productos, categorías y margen bruto estimado.

9. Regla fundamental de pagos
El comportamiento normal será un único método de pago por venta. El sistema soportará un segundo pago únicamente cuando sea necesario.
Caso normal:
Venta S/25.50 → Yape S/25.50

Caso normal:
Venta S/25.50 → Efectivo S/25.50

Caso excepcional:
Venta S/25.50 → Yape S/20.00 + Efectivo S/5.50
El modelo será Venta 1..N Pagos, pero la interfaz priorizará Efectivo, Yape y Plin, dejando Pago dividido como una opción secundaria.
Solo el componente pagado en efectivo incrementará el efectivo físico esperado de la caja.

18. Control de stock
Para el MVP, una venta que solicite una cantidad superior al stock disponible será rechazada. El backend deberá validar la disponibilidad, no únicamente el frontend.
La actualización deberá considerar concurrencia cuando dos dispositivos intenten vender simultáneamente las últimas unidades.

20. Costo y ganancia
El sistema distinguirá entre ingresos por ventas y margen bruto. Para calcular margen se requiere almacenar costo unitario.

El margen bruto no equivale a utilidad neta, porque esta última requiere considerar gastos operativos.

39. Reglas de negocio
Una venta debe contener al menos un producto.
La cantidad debe ser mayor que cero.
La suma de pagos debe ser igual al total.
Una venta confirmada no puede editarse libremente.
Una venta confirmada no se elimina físicamente.
Las anulaciones deben quedar auditadas.
Solo efectivo afecta el efectivo esperado.
Yape y Plin no aumentan el efectivo físico.
Un pago mixto debe sumar exactamente el total.
No se puede vender más stock del disponible bajo la política MVP.
No se puede cerrar una caja ya cerrada.
Un producto inactivo no puede agregarse a una nueva venta.
El precio histórico se conserva en cada detalle de venta.

54. Conclusión técnica
D' Kiram Pastelería debe construirse como un sistema transaccional de gestión comercial, no como un conjunto de CRUD independientes. La arquitectura separa producto, inventario, venta, pago, caja, movimiento de caja, empleado y turno para preservar integridad y trazabilidad.
El comportamiento normal de pago será un único método; el pago mixto se soportará como excepción. Solo la parte pagada en efectivo afecta el efectivo físico esperado de la caja.
La combinación React + TypeScript + PWA + Spring Boot + Java 21 + PostgreSQL/Supabase proporciona una base moderna, mantenible y preparada para crecimiento, evitando sobreingeniería en la primera versión.
La estrategia recomendada es implementar primero el núcleo transaccional —productos, inventario, ventas, pagos y caja— y posteriormente añadir reportes avanzados, clientes, pedidos, delivery, comprobantes electrónicos y analítica.
